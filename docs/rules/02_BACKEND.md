## 1. 아키텍처

### 아키텍처 스타일
- 상태: ✅ 결정
- 선택지:
  - **레이어드** — 단순, 혼자·소규모에 적합
  - **헥사고날(포트&어댑터)** — 협업·테스트 용이, 초기 비용 있음
  - **모듈러 모놀리스** — 도메인별 모듈 분리, 확장 대비
  - **멀티모듈** — 협업 시 모듈 단위 분담 가능
- 결정: **레이어드 + 순수 함수 코어 (functional core, imperative shell)**. 헥사고날은 쓰지 않는다.
- 이유:
  - 이 프로젝트는 단계가 순서대로 이어지는 파이프라인이고 Python이다. Port 계층 대신 순수 함수와 입출력 경계로 도메인을 격리한다.
  - 경계는 **실제로 바뀌는 곳(LLM 공급자, 캠프 데이터 출처)에만** 둔다.
  - 핵심 목적: 평가 스크립트가 DB·LLM 없이 `core.matching`을 직접 호출한다 (고정된 슬롯 JSON + 고정 캠프 데이터로 Hit@3 재계산).
  - 검토한 대안: 레이어드 단독(매칭 로직이 DB·LLM과 섞여 평가 재계산이 어려움), 헥사고날(파이프라인 규모에 비해 Port 계층 비용이 큼)
  - 전환 기준: 입출력 대상이 늘어 오케스트레이터가 감당하기 어려워지면 그 지점에 경계를 추가한다.
- 결정일: 2026-11-24

### 패키지 / 모듈 구조
- 상태: ✅ 결정
- 결정:
```
app/
├── routers/        FastAPI 엔드포인트 (글 등록, SSE, 피드백)
├── services/       오케스트레이션: DB 조회, LLM 호출, 단계 연결, 오류·측정 기록
├── repositories/   SQL 직접 작성, dataclass 반환 (ORM 없음)
├── sources/        캠프 출처·어휘 파일 읽기: load_camps_from_csv() → list[RawCamp]
├── llm/            LLMClient Protocol + groq.py, openrouter.py
├── core/           순수 함수: models, gate, merge, matching, reason (+ industry, job_relation, normalize_v2, slot_filling, evaluation)
├── config.py       .env 읽기, 공급자별 모델 선택
└── main.py         조립, 설정으로 LLM·출처 선택
scripts/   정규화·검사·평가 CLI
prompts/   프롬프트 본문(*.md). 읽기는 sources/, 조립은 core/ (05_AI.md)
eval/      정답 셋
data/      vocab(커밋) / private·derived·raw(git 제외)
frontend/  데모 페이지
```
  - 규칙:
    - **`core/`는 repositories, llm, sources, DB 드라이버, HTTP 클라이언트를 import하지 않는다.** 구조가 강제하지 않으므로 이를 검사하는 테스트를 둔다.
    - 오케스트레이터 비대화 방지: 단계별 측정·오류 처리는 작은 헬퍼로 감싸고, 기록은 recorder 하나에 모은다.
    - 피드백·검수 상태 변경 같은 단순 CRUD는 일반 routers/services/repositories로.
    - vocab·job_relation은 서버 시작 시 메모리 로드, 정규화 실행 후 갱신 API로 재로드.
  - 현재 구현된 것: `config.py`, `core/`(models, gate, merge, matching, reason, industry, job_relation, normalize, normalize_v2, slot_filling, evaluation), `llm/`, `services/slot_filling.py`(동기 호출 함수), `sources/`(vocab, prompts, qna, camps, evaluation). 나머지는 미구현.
- 결정일: 2026-11-24

## 2. API 설계 규칙

### API 스타일
- 상태: ✅ 결정
- 선택지: REST / GraphQL / gRPC / 혼합
- 결정: REST(JSON) + SSE(추천 결과 전달)
- 이유: 엔드포인트가 글 등록·피드백·결과 수신 몇 개뿐이다. 추천은 글 등록 후 백그라운드에서 만들어지므로 SSE로 밀어준다. SSE는 **DB에 저장된 추천 결과를 읽어 전송**한다(재접속 시에도 결과를 받을 수 있게).
- 결정일: 2026-11-24

### URL / 네이밍 규칙
- 상태: ✅ 결정
- 결정: `/api/{복수형 리소스}`, 케밥케이스, **버저닝 없음**. 운영 API는 `/api/admin/` 아래
```
POST /api/posts
GET  /api/posts/{post_id}/recommendations/stream   (SSE)
POST /api/recommendations/{rec_id}/feedback
POST /api/admin/vocab/reload
```
- 이유: 데모 단일 클라이언트라 호환성 관리 대상이 없음
- 결정일: 2026-11-25

### 공통 응답 포맷
- 상태: ✅ 결정
- 결정: **감싸지 않고 리소스를 그대로 반환** (FastAPI 기본 + Pydantic 응답 모델). 에러만 아래 에러 규약 형식
- 이유: `/docs` 자동 문서와 그대로 맞고, 프론트 TS 타입도 단순
- 결정일: 2026-11-25

### 에러 응답 규약
- 상태: ✅ 결정
- 결정: `{"error": {"code": "...", "message": "..."}}` + HTTP 상태코드
  - 400 `validation_error` (FastAPI 기본 422도 이 형식·상태로 바꾼다), 404 `not_found`, 500 `internal_error`
  - LLM 오류는 HTTP 오류가 아니다: 글 등록은 성공으로 응답하고, recommendation 레코드에 오류코드를 남긴다 (SSE로는 "추천 없음"과 같게 토스트 미표시)
- 결정일: 2026-11-25

## 4. 공통 처리 규칙

### 예외 처리 전략
- 상태: ✅ 결정
- 결정:
  - LLM 공급자 오류는 예외가 아니라 공통 반환 타입의 `error_code`로 돌려준다 (rate_limited, request_too_large, auth, bad_request, server_error, network, empty_response)
  - 파이프라인 중간 실패 시 성공한 단계 결과(예: 슬롯)는 오류코드와 함께 저장한다
  - 추천 0개 또는 게이트 종료는 오류가 아니라 정상 종료(토스트 없음, 로그만)
  - **전역 예외 핸들러 + 작은 예외 계층**: `AppError(code, status)` 하나와 `NotFoundError` 정도만 둔다. 전역 핸들러가 에러 규약 형식으로 변환하고, 예상 못 한 예외는 500 `internal_error`
  - 백그라운드 작업은 예외를 잡아 recommendation 레코드에 오류코드로 기록한다 (BackgroundTasks의 예외는 HTTP 응답으로 전달되지 않으므로)
- 결정일: 2026-11-25

### 로깅 규칙

## 5. 매칭 규칙

### 정렬 순서
- 상태: ✅ 결정
- 결정: 후보 조회는 SQL(모집 중 + 직무 A·B 등급), 정렬은 `core/matching.py`의 순수 함수로 **사전식** (가중합 아님)
  0. 모집 중 (모집기간 데이터가 없으면 모집 중으로 본다. 평가 때는 끈다)
  1. 직무 등급 A(SAME·CLOSE) / B(FAMILY) / 제외. B는 A가 3개 미만일 때만, 리뷰 플래그
  2. 산업 등급: 일치 > 계열 > ANY > 불일치
  3. 직무 SAME > CLOSE
  4. desired_help ↔ camp_type: 일치 > 선호 없음 > 불일치 (desired_help가 UNKNOWN이면 category 기본값, 그것도 없으면 건너뜀)
- 이유: 가중합은 보상 효과로 직무가 틀린 캠프가 산업·유사도 점수로 올라온다 (인턴십 프로젝트의 주된 오류). 앞 단계가 같을 때만 뒤 단계가 순서를 정한다
- 결정일: 2026-11-24

### 정렬 4단계(desired_help ↔ camp_type) 유지 여부
- 상태: ✅ 결정
- 선택지: 유지 / 유지하되 APPLICATION은 선호 없음으로 처리 / 제거
- 결정: **유지** (APPLICATION도 그대로 비교)
- 이유:
  - 정규화 v2 결과의 camp_type 분포(캠프 아님 제외)는 EXPERIENCE 64.4%, EXPLORE 35.4%, APPLICATION 0.3%. EXPLORE와 EXPERIENCE가 약 2:1로 갈려 있어 한 유형에 몰린 경우(효과 없음)가 아니다
  - 마지막 단계라 직무·산업 순서를 바꾸지 않고, 앞 단계 동점 안에서만 순서를 정한다
  - APPLICATION을 원하는 유저(자소서·면접)는 맞는 캠프가 거의 없어 이 단계가 사실상 동점으로 끝나지만 해는 없다. 별도 예외 규칙을 두면 규칙만 늘어난다
  - 제거하지 않은 이유: camp_type은 캠프명만 보고 LLM이 정한 값이고 검수 대상이 아니라 정확도는 확인하지 않았다. 다만 정렬에서 가장 약한 키라 틀려도 영향이 작고, 평가(3갈래 비교 ①은 camp_type이 없음)에서 효과를 따로 볼 수 있다
- 비고: 평가에서 이 단계 때문에 순위가 나빠진 사례가 나오면 다시 정한다
- 결정일: 2026-11-25

### sub_job(하위 직무) 정렬 키 여부
- 상태: ✅ 결정
- 선택지: 넣지 않음 / 직무 SAME·CLOSE 다음에 'sub_job 일치 > 미지정 > 불일치' 단계 추가
- 결정: **넣지 않음** (MVP)
- 이유:
  - 정규화 v2 결과에서 sub_job이 채워진 캠프는 18.0%이고, 대부분 원래 상세분류에서 왔다(LLM이 새로 채운 것은 1% 미만). 82%가 비어 있어 대부분 동점으로 끝난다
  - 같은 주 직무 안에서 sub_job이 2종 이상으로 갈리는 직무는 캠프가 2개 이상인 직무의 약 4분의 1이고, 그 직무들 안에서도 sub_job이 있는 캠프는 39%
  - 쓰려면 유저 쪽 슬롯필링에 sub_job 추출을 새로 넣어야 한다 (지금 슬롯: 직무·산업·desired_help)
- 비고: 평가에서 캠프가 많은 직무(연구개발, 공정기술 등) 안의 순서 오류가 보이면 다시 검토한다
- 결정일: 2026-11-25

### 게이트 (2단)
- 상태: ✅ 결정
- 결정: 게이트 종료 = 추천 없음(토스트 미표시). 오류가 아니라 정상 종료이고, 종료 사유 코드를 recommendation에 남긴다
  - **1차 (슬롯필링 전, 입력 필드만)** `core/gate.py`
    - `empty_post`: 제목과 본문이 모두 비어 있음
    - `off_target_group`: `question_category_group`이 `랜선 사수` (재직자의 회사생활 질문)
  - **2차 (병합 후)**
    - `no_signal`: 병합 결과에 직무도 산업도 없음
    - 직무는 없고 산업만 있으면 종료하지 않고 **산업만으로 매칭**한다 (아래 "직무 없이 산업만 있을 때")
- 이유:
  - 1차는 LLM 호출을 아끼는 컷이라 확실한 것만 자른다. `랜선 사수`는 기숙사·복장·근무 형태처럼 재직자의 회사생활 질문이 대부분이다. 재직자의 직무 전환 글을 일부 놓치지만 정밀도 우선 원칙에 맞다
  - `대학생 고민`·`이직 고민`은 1차에서 자르지 않는다: 전공·캡스톤·경력 전환 글에 직무 신호가 섞여 있다
  - question_category만으로 자르지 않는다: 추천이 필요한 글과 필요 없는 글이 같은 category에 섞여 있어 슬롯 기반 2차가 거른다
  - 검토한 대안: 빈 글만 컷(회사생활 질문마다 LLM 1회), `랜선 사수`+`대학생 고민` 컷(직무 신호가 있는 대학생 글까지 버림)
- 결정일: 2026-11-25

### 병합 (본문 명시 > 입력 필드 > 본문 추론)
- 상태: ✅ 결정
- 결정: `core/merge.py`. 직무와 산업을 **따로** 같은 규칙으로 병합한다
  - 출처: 본문 명시(슬롯 basis=EXPLICIT) / 입력 필드(희망 직무의 사전 변환 직무·산업, 목표 회사의 산업) / 본문 추론(basis=INFERRED)
  - 후보 = 본문 명시 ∪ 입력 필드 (이 순서로, 중복은 앞 출처를 남김)
  - **본문 명시와 입력 필드가 모두 있고 겹치는 값이 하나도 없으면 둘 다 후보로 두고 충돌 플래그**(`job_conflict` / `industry_conflict`)
  - **본문 추론 값은 본문 명시·입력 필드가 하나도 없을 때만** 후보로 쓰고 `job_inferred_only` / `industry_inferred_only` 플래그. 명시·필드 값이 있으면 추론 값은 버리고 로그에 남긴다
  - 사전에 없는 입력 필드 표기(변환 결과 없음)는 후보를 만들지 않고 로그에 남긴다 (슬롯필링에는 힌트로 이미 들어감)
  - 후보마다 출처와 근거 표기를 둔다: 본문이면 raw_mention, 입력 필드면 필드 원문 표기. 사유 문장이 이것만 쓴다
  - desired_help: 슬롯 값이 UNKNOWN이 아니면 그 값(출처 본문), UNKNOWN이면 `category_camp_type` 기본값(출처 category), 기본값이 빈 값이거나 없으면 선호 없음(정렬 4단계 건너뜀)
- 이유:
  - 본문 명시가 입력 필드보다 앞서는 것: 입력 필드는 글쓴이가 고른 넓은 값이거나 예전 값인 경우가 있고, 본문은 지금 고민을 직접 말한다
  - 충돌 시 둘 다 두는 것: 어느 쪽이 맞는지 룰로 판단할 근거가 없다. 한쪽을 버리면 평가 판정 기준 2(명시한 직무가 빠지면 오답)에 걸린다
  - 추론 값을 제한하는 것: 정밀도 우선. 명시·필드 값이 있는데 추론 값까지 넣으면 후보 직무가 늘어 직무별 분배가 엉뚱한 직무에 자리를 준다 (대안: 추론 값도 항상 후순위 후보로 — 후보가 늘어 오추천 위험)
- 결정일: 2026-11-25

### 정렬 키 계산 세부
- 상태: ✅ 결정
- 결정: `core/matching.py`
  - 캠프의 직무가 여럿이고 유저 후보 직무가 여럿이면, 모든 (유저 직무, 캠프 직무) 쌍 중 **정렬 키가 가장 좋은 쌍**으로 본다. 그 유저 직무가 "맞춘 직무"이고 사유에 쓴다 (동점이면 병합 순서가 앞선 유저 직무)
  - 관계: 같은 직무면 SAME, 아니면 job_relation(CLOSE/FAMILY), 없으면 제외
  - B등급(FAMILY)은 **모집 중 후보 전체에서 A등급 캠프가 3개 미만일 때만** 넣고 카드에 리뷰 플래그. 사전식 정렬이라 B는 항상 A 뒤에 온다
  - 산업 등급은 `core/industry.py`의 `industry_grade`. 유저 산업이 없으면 이 단계를 건너뛴다. 사유용 "맞춘 산업"은 그 등급을 만드는 유저 산업 중 병합 순서가 앞선 것
  - camp_type 단계: 일치 > 캠프 camp_type 없음 > 불일치. 선호 없음이면 건너뜀
  - 마지막 동점은 캠프 ID 순 (실행마다 같은 결과가 나오게. 품질 의미는 없음)
  - 0단계(모집 중)는 `check_recruiting` 인자로 끈다 (평가)
- 결정일: 2026-11-25

### 복수 직무 분배
- 상태: ✅ 결정
- 결정: 후보 직무가 2개 이상이면 **직무마다 1자리를 보장**한다
  1. 병합 순서 앞 3개 직무에 대해, 순서대로 그 직무 기준 정렬 키가 가장 좋은 **A등급** 캠프 중 아직 뽑히지 않은 것을 하나씩 뽑는다. 그 직무에 A등급 캠프가 없으면 보장 없음
  2. 남은 자리는 나머지 캠프를 전체 정렬 순으로 채운다
  3. **표시 순서는 뽑힌 캠프들을 전체 정렬 키로 다시 정렬**한 순서 (보장으로 뽑힌 캠프도 키가 나쁘면 뒤에 선다)
- 이유:
  - 평가 경계 규칙 3(대등하게 언급한 직무마다 상위 3개에 하나 이상)과 판정 기준 2(명시한 직무가 빠지면 오답)를 따르는 동작. 분배가 없으면 산업까지 맞는 한 직무가 3자리를 다 차지한다
  - A등급만 보장하는 것: 그 직무의 캠프가 없을 때 FAMILY로 자리를 채우면 "다른 직무로 대체"(판정 기준 3의 오답 예)가 된다
  - 표시 순서를 다시 정렬하는 것: 사전식 원칙(앞 단계가 같을 때만 뒤 단계가 순서를 정함)을 표시 순서에서도 지킨다. 분배는 "무엇을 넣을지"만 바꾼다
  - 검토한 대안: 분배 없이 단일 정렬(한 직무가 독식), 본문 명시 직무만 보장(필드와 본문이 충돌하는 글에서 필드 직무가 빠짐)
- 결정일: 2026-11-25

### 직무 없이 산업만 있을 때
- 상태: ✅ 결정
- 결정: 병합 결과에 직무가 없고 산업만 있으면 **산업만으로 매칭**한다
  - 후보: 산업 등급이 **일치 또는 계열**인 캠프만 (ANY·불일치 제외). 직무 단계(1·3)는 건너뛰고 분배도 없다
  - 정렬: 산업 등급 > camp_type 단계 > 캠프 ID
  - 모든 카드에 리뷰 플래그, 결과에 `industry_only` 플래그
- 이유:
  - 사용자 결정: 직무 없이 산업만 말한 글(예: 특정 업종 회사를 목표로 무엇을 준비할지)도 추천 대상으로 본다
  - ANY를 빼는 것: 산업무관 캠프는 직무도 산업도 맞춘 근거가 없어 사유를 쓸 수 없다
  - 대안 "직무 없으면 종료"는 이 글들을 모두 추천 없음으로 끝낸다. 리뷰 플래그로 평가에서 이 모드의 정밀도를 따로 본다
- 결정일: 2026-11-25

### 추천 사유 (템플릿)
- 상태: ✅ 결정
- 결정: `core/reason.py`. 근거는 **병합 후보의 근거 표기(본문 raw_mention 또는 입력 필드 원문)와 매칭에 쓰인 값(캠프의 대표 직무·산업, camp_type)**만. 카드당 1~3문장
  - 근거 앞말: 본문이면 `글에 쓴 '{발췌}'`, 희망 직무 필드면 `희망 직무 '{표기}'`, 목표 회사 필드면 `목표 회사 '{표기}'`
  - 직무 문장: SAME `{근거}에 맞춘 {캠프 직무} 캠프예요.` / CLOSE `{근거}에 가까운 {캠프 직무} 캠프예요.` / FAMILY `{근거}에서 넓혀 찾은 같은 직군의 {캠프 직무} 캠프예요.`
  - 산업 문장: 일치 `{근거} 분야를 다뤄요.`(본문) · `{근거}의 {캠프 산업} 분야를 다뤄요.`(입력 필드: 회사명·직무명이라 업종을 밝힘) / 계열 `{근거}에 가까운 {캠프 산업} 분야예요.` / ANY `산업과 무관하게 들을 수 있어요.` / 불일치·건너뜀은 문장 없음
  - 산업만 매칭: 직무 문장 대신 산업 문장만
  - camp_type 문장: 일치이고 desired_help 출처가 본문일 때만 `{help 발췌}에 맞는 {유형} 과정이에요.` (유형: EXPLORE 직무 탐색형, EXPERIENCE 실무 경험형, APPLICATION 지원 준비형)
  - 조사는 `에`·`의`처럼 받침과 무관한 것만 쓴다 (발췌가 영문·숫자로 끝나도 문장이 깨지지 않게)
- 이유: 사유는 유저가 쓴 말과 실제 매칭 근거만 보여줘야 신뢰가 생긴다. LLM 생성 사유는 근거에 없는 말을 지어낼 수 있고 요청당 호출이 하나 늘어 MVP에서 제외 (05_AI.md). category 기본값으로 정한 camp_type은 유저가 쓴 말이 아니라 문장에 넣지 않는다
- 결정일: 2026-11-25
