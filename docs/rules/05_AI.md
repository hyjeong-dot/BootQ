# 05. AI 기능 설계

> 문서 상태: ✅ 완료 (2026-11-25)
> AI 기능이 없는 프로젝트라면 이 문서 전체를 ➖ 해당없음 처리한다.
> 사전 기입(2026-11-24): 기존 설계 메모와 이미 구현된 LLM 경계(`app/llm/`)에서 옮겼다.

## 1. AI 사용 목적

### 이 프로젝트에서 AI가 하는 일
- 상태: ✅ 결정
- 원칙: **결정 가능한 판단은 룰/SQL, 의미 해석만 LLM**
- 결정:
  1. **캠프 정규화 (오프라인)** — 캠프명을 읽고 규칙 기준선에 없는 **추가분만** 낸다(추가 직무·산업·하위직무·스킬·태그·camp_type). 기준의 주 직무·하위직무·산업은 코드가 유지한다
  2. **슬롯필링 (요청 시점, 요청당 1회)** — 글 제목+본문 → 직무 후보[], 산업[], desired_help(EXPLORE / EXPERIENCE / APPLICATION / UNKNOWN), 원문 발췌(raw_mention), 근거(명시/추론/없음). 입력 필드 정규화 결과를 힌트로 제공
  3. **평가 비교군 ③** — 같은 모델에 캠프 전체 목록을 주고 고르게 하는 베이스라인 (평가 전용)
  - LLM을 쓰지 않는 것: 게이트, 병합, 매칭 정렬, 추천 사유(MVP는 템플릿 문장)
- 결정일: 2026-11-24

## 2. 모델 선택

### 모델 및 실행 방식
- 상태: ✅ 결정
- 선택지:
  - **로컬 모델** (Ollama 등) — 무료, 하드웨어 제약(예: RTX 4060 8GB → 9B 이하 권장), 품질 한계
  - **API 모델** (Claude, Gemini, GPT 등) — 고품질, 비용 발생, 키 관리 필요
  - **혼합** — 간단한 작업은 로컬, 중요한 작업은 API
- 결정: API 모델
  - 메인: **Groq 무료 티어 `openai/gpt-oss-120b`** — 슬롯필링과 정규화
  - 베이스라인(③): **OpenRouter의 같은 모델** — 요청당 입력이 커서 Groq 분당 토큰 한도를 넘기 때문. 학습 미사용 설정을 켠다. 평가 단계에서 확인한 결과 무료 버전이 없어 유료로 실행했다(2026-11-25, 23건과 시험 호출 합계 약 $0.05. 무료 모델은 다른 모델이라 "같은 모델" 비교가 깨지고, 무료 공급자는 대부분 프롬프트를 학습에 써서 캠프 목록을 보낼 수 없음)
  - 공급자는 `llm/`의 Protocol 뒤에 두고 설정으로 교체
- 이유: strict JSON schema 지원, 입력을 학습에 쓰지 않음, 무료. Gemini는 무료 티어 입력이 학습에 쓰이고(EU 외) 최신 모델의 일일 한도가 작아 제외
- 결정일: 2026-11-24

### 비용 / 사용량 한도
- 상태: ✅ 결정
- 결정:
  - 비용 0 (무료 티어). Groq 무료 한도(콘솔 확인값): 30 RPM, 1K RPD, **8K TPM, 200K TPD**
  - 정규화는 분당 1회로 간격을 두고, 하루 한도를 넘으면 다음 날 이어서 (멱등 실행이라 중단 후 재개 가능)
  - 한도 정보는 응답 헤더에서 읽어 `LLMResult.meta`에 남긴다
- 결정일: 2026-11-24

## 3. 호출 구조

### 호출 위치 및 방식
- 상태: ✅ 결정
- 결정:
  - 백엔드에서만 호출. 글 등록 후 **FastAPI BackgroundTasks**에서 실행, 결과는 DB 저장 후 SSE로 전달 (LLM 스트리밍 없음)
  - LLM 클라이언트는 동기(`urllib`)이므로 async services에서 `asyncio.to_thread`로 호출 (04_DATABASE.md)
  - 모든 공급자는 같은 반환 타입 `LLMResult`(텍스트, 입력·출력 토큰, 소요시간, 오류코드, meta) — 공급자마다 토큰·오류 기록이 어긋나지 않게
  - 타임아웃·재시도 (클라이언트 생성 시 용도별로 지정):
    | 용도 | 타임아웃 | 최대 재시도 | 이유 |
    |---|---|---|---|
    | 슬롯필링 (요청 시점) | **15초** | **1회** | 글 올린 직후 노출이라 늦은 토스트는 가치가 낮음 (최악 약 30초) |
    | 정규화·평가 (오프라인) | 90초 | 3회 | 현재 구현 기본값 유지 |
- 결정일: 2026-11-25

### 실패 시 폴백
- 상태: ✅ 결정
- 결정:
  - 재시도 대상: 429·5xx·네트워크 오류만. 대기 = max(retry-after, 2초×시도횟수), 최대 60초. 그 외 오류는 즉시 오류코드 반환 (현재 구현)
  - **슬롯필링 최종 실패 → 추천 없음으로 종료**: 오류코드를 recommendation에 기록하고 토스트 미표시. 입력 필드만으로 매칭을 계속하지 않는다
  - 중간 실패 시 성공한 단계 결과는 오류코드와 함께 저장
- 이유: 정밀도 > 재현율. 입력 필드는 "모든 직무·모든 회사"가 대부분이고, 필드·본문이 충돌하는 글을 본문 없이 판단하면 틀릴 수 있음
- 결정일: 2026-11-25

## 4. 프롬프트 관리

### 프롬프트 저장 위치 / 버전 관리
- 상태: ✅ 결정
- 선택지: 코드 내 상수 / 별도 파일(`prompts/` 폴더) / DB
- 결정: **본문은 `prompts/*.md`, 조립은 core의 순수 함수**
  - 지시문 본문(고정 텍스트)은 `prompts/` 아래 마크다운 파일 (예: `prompts/slot_filling.md`, `prompts/normalize_v2.md`)
  - 파일 읽기는 `sources/`가 하고, 읽은 텍스트를 core의 조립 함수(`build_system_prompt` 등)에 인자로 넘긴다 — **core는 파일을 읽지 않는다** (02_BACKEND.md import 규칙 유지)
  - **슬롯필링 프롬프트의 Enum 목록은 vocab에서 자동 생성**해 조립 단계에서 끼워 넣는다
  - 버전: 정규화 결과에는 `normalizer_version`을 저장하고, 버전이 바뀌면 전체 재실행 후 이전 버전과의 diff만 검수. 슬롯필링도 프롬프트 버전 상수를 recommendation에 저장
  - 프롬프트 파일을 바꾸면 버전 상수도 함께 올린다 (정규화 캐시 키에 프롬프트 본문이 들어가 있으므로 재실행 대상도 자동으로 바뀜)
- 이유: 긴 지시문을 코드와 분리해 읽고 고치기 쉽게 (사용자 선택. AI 추천은 core 함수 안에 그대로 두는 것이었음 — 이전 작업이 생기기 때문)
- 구현 (2026-11-25, #5):
  - 본문 `prompts/normalize_v2.md`, 자리표시는 `string.Template` 형식 `${jobs}`, `${industries}`, `${sub_jobs}`, `${skills}` (모르는 자리표시는 KeyError)
  - 읽기 `app/sources/prompts.py`의 `load_prompt(name)` — 파일 끝 줄바꿈 하나는 프롬프트에 넣지 않음
  - 조립 `app/core/normalize_v2.build_system_prompt(vocab, template)`
  - 이전 전 출력과 같은지 `tests/test_prompts.py`가 고정 파일(`tests/fixtures/normalize_v2_system_prompt.txt`)로 검사
  - v1 정규화 프롬프트(`app/core/normalize.py`)는 과거 결과 비교용으로만 남아 있어 옮기지 않았다
- 결정일: 2026-11-25

### 응답 형식 강제 방식
- 상태: ✅ 결정
- 선택지: JSON 스키마(structured output) / 파싱 + 검증 / 자유 텍스트
- 결정: JSON 스키마(strict structured output) **+ 응답 후 코드 검증** (vocab에 있는 값인지, 근거 구절이 원문(캠프명·글)에 실제로 있는지). 정규화에서 주 직무 교체는 자리표시 직무에서만 허용하고, 그 외 교체 시도는 버리고 기록한다
- 결정일: 2026-11-24

### 슬롯필링 입출력·검증 (#12)
- 상태: ✅ 결정
- 결정:
  - 입력: 글 제목+본문, 입력 필드 힌트(희망 직무·목표 회사의 **원문 표기 + 사전 변환 결과**). 사전에 없는 표기도 표기만 넘긴다. 미지정(모든 직무·모든 회사)과 사전에서 제외한 표기는 넘기지 않는다. question_category는 넘기지 않는다
  - 출력 (strict schema, Enum은 vocab에서 자동 생성 — 직무는 '임시' 제외, 산업은 ANY 제외):
    `jobs[{job, raw_mention, basis}]`, `industries[{industry, raw_mention, basis}]`, `desired_help`(EXPLORE / EXPERIENCE / APPLICATION / UNKNOWN), `help_mention`
    - basis는 값마다 EXPLICIT(명시) / INFERRED(추론). 근거 '없음'은 빈 배열
    - LLM은 **본문 근거만** 낸다. 입력 필드 값은 병합 단계(#10)가 직접 넣으므로 힌트로만 준다
  - 응답 후 검증 (`app/core/slot_filling.parse_response`):
    - 어휘 밖 값, **raw_mention이 제목+본문에 없는 값**(공백·대소문자 무시)은 버린다. 중복 제거, 직무·산업 각 최대 3개(넘으면 뒤를 버림). 버린 값과 이유는 `log`에
    - desired_help의 help_mention이 글에 없으면 UNKNOWN으로 (UNKNOWN이면 category 기본값으로 보완되므로)
    - JSON이 아니거나 형식이 스키마와 다르면 `slot_parse_error` / `slot_schema_error`. 공급자 오류는 LLMResult의 오류코드를 그대로. 어느 경우든 호출자는 추천 없음으로 끝낸다
- 이유:
  - 발췌가 없는 값을 버리는 것: 정밀도 우선. 추천 사유가 raw_mention을 근거로 쓰므로 글에 없는 발췌로는 사유를 만들 수 없다 (대안: basis를 INFERRED로 낮춰 값은 남기기 — 근거 없는 값이 남아 제외)
  - 필드 원문 표기를 함께 주는 것: 사전에 없는 자유 표기(예: 세부 직무명)도 본문 해석에 참고가 된다 (대안: 변환 결과만 — 사전 밖 표기가 버려짐)
  - category를 주지 않는 것: desired_help가 category에 끌려가지 않게. category는 desired_help가 UNKNOWN일 때만 기본값으로 쓴다
  - maxItems를 스키마에 넣지 않고 코드가 자르는 것: 공급자마다 strict 모드의 지원 범위가 달라서
- 구현:
  - 본문 `prompts/slot_filling.md` (자리표시 `${jobs}`, `${industries}`), 버전 상수 `SLOT_PROMPT_VERSION = 'slot-v1'`
  - core `app/core/slot_filling.py`: 필드 힌트(`job_field_hint`, `company_field_hint`), `build_schema`, `build_system_prompt`, `build_user_prompt`, `parse_response`
  - 호출 `app/services/slot_filling.py`: `make_slot_client`(타임아웃 15초·재시도 1회), `fill_slots(client, input, vocab, template) -> (SlotResult, 측정값)` (동기. async 서비스에서 `asyncio.to_thread`로)
  - 어휘 `app/sources/vocab.load_slot_vocab()` (파일 순서 유지 — 프롬프트가 실행마다 같도록)
  - 시험 `scripts/try_slot_filling.py`: 재작성한 평가 질문만 보낸다. 결과는 `data/derived/slot_trial.jsonl`
- 결정일: 2026-11-25

## 5. 품질 관리

### 결과 평가 / 테스트 방법
- 상태: ✅ 결정
- 결정: `docs/EVAL.md` — 재작성한 질문 18개의 정답 셋을 시스템 결과를 보기 전에 판정·고정. 슬롯 정확도와 매칭 정확도를 분리 측정. 3갈래 비교(규칙+수동 / +LLM 정규화 / LLM 캠프 선택). 정규화는 기준선과 달라진 캠프만 diff 검수
- 결정일: 2026-11-24

### 안전장치
- 상태: ✅ 결정
- 결정:
  - 무료 LLM 티어에 **실제 유저 글을 대량으로 보내지 않는다** (입력이 서비스 개선에 쓰일 수 있음). 개발·평가에는 재작성한 샘플 사용, 원문은 LLM에 보내지 않음
  - 정밀도 > 재현율: 애매하면 추천하지 않는다 (글 올린 직후 엉뚱한 추천은 광고로 느껴짐)
  - LLM은 기준값을 덮어쓰지 못한다. 사람이 확정한 수동 보정은 코드가 적용하고 LLM에 맡기지 않는다
  - LLM 결과가 기존 코드와 다르면 pending_review — 승인 전에는 기존 코드 기준으로만 추천 후보에 넣는다
- 결정일: 2026-11-24
