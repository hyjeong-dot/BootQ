# 평가 설계

## 원칙: 정답은 시스템보다 먼저 정한다

- 정답 셋(허용 캠프, 추천 없음 여부)은 **시스템 결과를 보기 전에** 사람이 판정하고 고정한다. 판정이 끝난 뒤 커밋해서 이후 수정 이력이 남게 한다.
- 허용 캠프 후보는 **원본 캠프명과 원래 직무코드·산업만** 보고 뽑는다. 정규화 결과(camp_profile), 직무 관계(job_relation), 산업 계열(industry_family), 매칭 코드는 쓰지 않는다. 정답이 시스템의 판단 기준을 닮으면 평가가 시스템을 검증하지 못한다.
- 질문은 실제 유저 글을 **재작성한 것**을 쓴다. 직무·산업·회사·고민 유형, 그리고 입력 필드와 본문이 서로 다른 구조는 그대로 둔다. 원문은 커밋하지 않고 LLM에도 보내지 않는다.
- 평가 질문은 이전 인턴십 프로젝트의 테스트 질문 18개에서 왔다. 그 프로젝트의 👍/👎 라벨은 정답으로 쓰지 않는다. 버전별 출력에 대한 판정이었고 측정 도중 기준이 바뀌었기 때문이다.

## 판정 기준

이전 인턴십 프로젝트의 최종 평가 기준을 그대로 출발점으로 삼는다.

1. **명시한 직무·산업에 맞는 캠프가 먼저(상위에) 있으면, 산업을 넓혀 추천한 2·3순위도 허용한다.**
2. **고민에 명시된 직무가 추천에서 빠지면 오답으로 본다.**
3. **캠프 공급 부족은 산업·분야가 넓어지는 경우에 한해 개별 추천의 오류로 보지 않는다.**
   - 허용: 금융 전용 데이터 캠프가 없어 금융·IT 데이터 캠프를 추천한 경우 (직무는 같고 산업만 넓어짐)
   - 오답: 명시한 직무 자체의 캠프가 없어 **다른 직무** 캠프로 대체된 경우 (예: 제약 BD 캠프가 없어 임상 CRA 캠프를 추천)

### 측정 전에 정해야 하는 경계 사례

인턴십에서는 아래 유형에 측정 시점마다 다른 라벨이 붙어 지표가 흔들렸다. 판정 전에 규칙을 정해 여기에 적는다.

| 유형 | 예 | 규칙 |
|---|---|---|
| 1·2순위는 정확하고 3순위만 다른 직무 | 플랜트 공정설계 질문에 3순위가 다른 직무 캠프 | (판정 전 결정) |
| 핵심 직무는 맞지만 본문의 산업이 반영되지 않음 | "자동차 영업"인데 산업무관 영업 캠프만 | (판정 전 결정) |
| 여러 직무를 언급했는데 일부만 반영 | 무역·물류 중 무역 캠프만 | (판정 전 결정) |

## 판정 단위

- **캠프별 허용/불허**: 질문마다 후보 캠프를 하나씩 보고 허용/불허를 정한다. 허용된 캠프가 그 질문의 `allowed_camp_ids`가 된다.
- **추천 없음이 정답인 질문**: 직무·산업 신호가 없거나 캠프 추천이 도움이 되지 않는 고민. 이 질문에서는 아무것도 추천하지 않아야 정답이다.
- **후보에 없는 캠프를 시스템이 추천한 경우**: 시스템 결과를 낸 뒤 그런 캠프만 모아서, 어느 시스템이 냈는지 가린 채 같은 기준으로 추가 판정한다(블라인드 풀링). 추가 판정 전에는 불허로 센다.

## 지표

슬롯 정확도와 매칭 정확도를 **분리**해서 잰다. 슬롯이 틀려서 매칭이 틀린 것과 매칭 규칙이 틀린 것을 구분하기 위해서다.

| 지표 | 정의 |
|---|---|
| 슬롯 정확도 (직무·산업) | 추출된 직무·산업이 `expected_jobs`, `expected_industries`와 맞는 비율 |
| Hit@3 | 추천이 필요한 질문 중, 상위 3개에 허용 캠프가 하나 이상 있는 비율 |
| Precision@3 | 추천된 캠프 중 허용 캠프의 비율 |
| 추천 없음 정답률 | 추천 없음이 정답인 질문에서 추천하지 않은 비율, 추천이 필요한 질문에서 추천한 비율 |
| 토큰·응답 시간 | 질문당 평균 (같은 공급자끼리만 시간 비교) |

## 비교 대상 (3갈래)

같은 정답 셋으로 세 가지를 비교한다. LLM을 어디에 쓰는 것이 정확도에 얼마나 기여하는지를 분리해서 보기 위해서다.

| | 캠프 프로파일 | 캠프 선택 |
|---|---|---|
| ① 규칙+수동 | 기존 코드를 규칙으로 옮긴 기준선 + 사람의 수동 보정 | 매칭 규칙 |
| ② 규칙+수동+LLM | ①에 LLM 정규화의 추가분을 합친 것 | 매칭 규칙 |
| ③ LLM 캠프 선택 | (쓰지 않음) | 같은 모델에 캠프 전체 목록을 주고 고르게 함 |

- 수동 보정은 사람이 한 작업이므로 ①과 ②에 똑같이 적용한다. 그래야 ①→②의 차이가 LLM 정규화의 기여만 보여준다.
- ①에는 camp_type이 없어 매칭 정렬의 마지막 단계(유저 니즈 ↔ camp_type)가 빠진다. ①과 ②의 차이에는 이 단계의 효과도 섞여 있다는 점을 결과에 함께 적는다.
- ③은 요청당 입력이 커서(캠프 전체 목록) 무료 티어의 분당 토큰 한도에 걸리는 공급자를 피해 실행한다. 정확도는 같은 모델끼리 비교하고, 응답 시간은 공급자가 다르면 직접 비교하지 않는다.
- 이전 인턴십 프로젝트의 수치와는 직접 비교하지 않는다 (캠프 풀, 시점, 모델, 질문이 모두 다르다).

## 산업 계열 결정용 확인

- 전자/기계 산업의 품질관리 유형 질문에서, 전자·반도체 계열을 넣은 경우와 뺀 경우의 추천을 비교해 계열 포함 여부를 최종 결정한다.
- 국제무역·물류 유형 질문에서 물류 캠프가 물류·무역 계열 일치로 올라오는지 확인한다.

## 파일

| 파일 | git | 내용 |
|---|---|---|
| `eval/answer_set_template.csv` | 커밋 | 정답 셋 형식 (빈 템플릿) |
| `eval/answer_set.csv` | 커밋 | 재작성 질문 18개. 판정 칸은 판정 후 채운다 |
| `data/private/eval_rewrite_review.csv` | 제외 | 원문과 재작성본 대조 (의미 확인용) |
| `data/private/eval_candidates.csv` | 제외 | 질문별 후보 캠프 10~15개와 고른 이유, 판정 칸 |

정답 셋 컬럼:

| 컬럼 | 뜻 |
|---|---|
| `eval_id` | 평가 질문 ID (E01~). 원문 ID와의 대응은 비공개 파일에만 둔다 |
| `title`, `content` | 재작성한 제목·본문 |
| `target_job`, `target_company`, `category`, `category_group` | 입력 필드 (원문과 같은 값) |
| `expected_jobs`, `expected_industries` | 슬롯 정답 (대표 직무·대표 산업 어휘, 여러 개면 `\|`로 구분) |
| `no_recommendation` | 추천 없음이 정답이면 `Y`, 아니면 `N` |
| `allowed_camp_ids` | 허용 캠프의 `source_camp_id` (`\|`로 구분) |
| `notes` | 입력 필드와 본문이 충돌하는 구조 등 |

## 판정 절차

1. `eval_rewrite_review.csv`에서 재작성본의 의미가 원문과 같은지 확인한다.
2. 위 "경계 사례" 규칙을 정한다.
3. `eval_candidates.csv`에서 후보마다 허용/불허를 판정하고, 질문마다 추천 없음 여부를 정한다.
4. 판정 결과를 `answer_set.csv`에 옮기고 커밋해서 고정한다.
5. 그다음에 시스템을 실행하고 결과를 본다.
